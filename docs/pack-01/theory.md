## Блок 1 — Docker networking

*Закрывается задачами 1.1, 1.2, 2.1*

| ☐ | Понятие | Что значит «знаю» |
|---|---|---|
| ☐ | **Network namespace** | Почему у контейнера свой `localhost`, свои интерфейсы и своя таблица маршрутов — и почему из-за этого `127.0.0.1` внутри контейнера не имеет отношения ни к хосту, ни к соседу |
| ☐ | **Драйвер `bridge`** | Что Docker создаёт на хосте: виртуальный мост, подсеть, NAT наружу |
| ☐ | **Дефолтная bridge vs пользовательская** | Резолв по имени есть только во второй; в первой — только по IP. Это причина большинства «не видит соседа» |
| ☐ | **Встроенный DNS Docker** | Резолвер на `127.0.0.11` внутри контейнера; он и превращает имя сервиса в адрес |
| ☐ | **Драйвер `host`** | Контейнер в namespace хоста: изоляции сети нет, порты не публикуются, конфликты портов настоящие |
| ☐ | **Драйвер `none`** | Знать, что существует, и когда применяется |
| ☐ | **Публикация порта (`ports:`)** | Проброс `host:container` через NAT — единственный способ попасть снаружи VM |
| ☐ | **`expose:`** | Декларация, а не публикация. Ничего наружу не открывает |
| ☐ | **Привязка к интерфейсу** | `0.0.0.0:8080` слушает на всех интерфейсах, `127.0.0.1:8080` — только локально. Разница между «работает у меня» и «открыто в интернет» |
| ☐ | **Сети в Compose** | Дефолтная сеть проекта, именованные сети, `external: true`, и почему два отдельных `docker compose up` не оказываются в одной сети |
| ☐ | **Имя сервиса как адрес** | В Compose обращение идёт к `имя_сервиса:порт_внутри`, не к опубликованному порту |
| ☐ | **Инспекция** | `docker network ls`, `docker network inspect`, `docker inspect` — где смотреть фактическое состояние, а не предполагаемое |

**Итоговая проверка блока:** взять любые два контейнера своего стенда и без запуска команд предсказать, увидят ли они друг друга по имени. Потом проверить. Совпало — блок закрыт.

## Блок 2 — TCP, DNS и диагностика

*Закрывается задачей 1.3, применяется в 2.1*

| ☐ | Понятие | Что значит «знаю» |
|---|---|---|
| ☐ | **Трёхстороннее рукопожатие** | SYN → SYN-ACK → ACK; зачем три пакета, а не два; что стороны согласуют |
| ☐ | **Флаги TCP в выводе tcpdump** | `[S]` = SYN, `[S.]` = SYN-ACK, `[.]` = ACK, `[R]` = RST, `[F]` = FIN |
| ☐ | **RST vs таймаут** | Отказ порта отличается от «пакет не дошёл». Первое — мгновенно, второе — висит. Это первое разветвление при отладке связности |
| ☐ | **Listening socket** | Что значит «процесс слушает порт», на каком интерфейсе, каким процессом — вывод `ss -tulpn` целиком |
| ☐ | **Порядок разрешения имени** | `/etc/hosts` → DNS-резолвер → ответ; и что внутри контейнера этот путь другой, чем на хосте |
| ☐ | **Запись A, TTL, авторитетность** | Достаточно, чтобы читать вывод `dig` и не гадать |
| ☐ | **Маршрут по умолчанию** | `ip route`: куда уходит пакет, если получатель не в локальной сети |
| ☐ | **Этапы `curl -v`** | Резолв имени → установка TCP → (TLS) → отправка запроса → ответ. Уметь показать границу каждого этапа в выводе |
| ☐ | **BPF-фильтр** | Достаточно, чтобы писать `port 3000`, `host X`, `tcp` и комбинации — не больше |
| ☐ | **Четыре точки отказа связности** | Не туда пошёл → не дошёл → некому принять → ответ не вернулся. Диагностика — это выбор между ними |

**Итоговая проверка блока:** сломать связность на стенде специально (остановить контейнер, поменять порт, убрать из сети) и по одному только выводу инструментов сказать, что именно сломано, — до того как посмотришь, что сделал.

## Блок 3 — CI/CD, первые понятия

*Закрывается задачами 2.1, 2.2, 2.3, 2.4*

| ☐ | Понятие | Что значит «знаю» |
|---|---|---|
| ☐ | **Runner** | Отдельный процесс, который забирает джобы у GitLab. Живёт где угодно, но **должен дозвониться** до GitLab — отсюда вся поломка |
| ☐ | **Регистрация runner-а** | Токен, привязка, `gitlab-runner verify`, где он виден в UI |
| ☐ | **Executor** | Чем и где выполняется джоба (`shell`, `docker`, …) — и что от этого зависит сетевая доступность |
| ☐ | **`external_url` / clone URL** | Почему адрес, работающий из браузера, может быть недостижим изнутри контейнера. Классическая причина «runner не подключается» |
| ☐ | **Pipeline, stage, job** | Иерархия и порядок; что выполняется параллельно, что последовательно |
| ☐ | **`.gitlab-ci.yml`** | Структура: `stages`, `image`, `script`, `only/rules`. Уметь прочитать чужой файл |
| ☐ | **Container registry** | Что это такое, как выглядит полный адрес образа, зачем аутентификация |
| ☐ | **Тег образа** | Идентификатор версии. `latest` — это подвижная ссылка, а не версия |
| ☐ | **Воспроизводимость** | Почему тег по commit SHA даёт однозначное соответствие «код ↔ образ», а `latest` — нет. Один из самых частых вопросов на собеседовании |
| ☐ | **Предопределённые переменные** | `CI_COMMIT_SHORT_SHA`, `CI_REGISTRY_IMAGE`, `CI_COMMIT_REF_SLUG` — откуда берутся значения |
| ☐ | **Артефакт сборки** | Образ как единица доставки: собран один раз, дальше только продвигается по средам |

**Итоговая проверка блока:** объяснить за три минуты, что происходит между `git push` и работающим контейнером на VM. По шагам, называя, где что выполняется.

## Блок 4 — Метод

*Закрывается задачами 2.1, 3.1, 4.1. Формально не «теория», но именно это отличает инженера от исполнителя гайдов*

| ☐ | Понятие | Что значит «знаю» |
|---|---|---|
| ☐ | **Гипотеза с фальсификацией** | До запуска команды знать, **какой результат опровергнет** гипотезу. Иначе это не проверка, а подтверждение |
| ☐ | **Деление пополам** | Каждой проверкой отсекать половину пространства поиска, а не проверять по одному кандидату |
| ☐ | **Отрицательный результат** | Отпавшая гипотеза сужает поиск так же, как подтвердившаяся. Стирать её — терять работу |
| ☐ | **Наблюдение vs предположение** | «Контейнер в сети X» (посмотрел) и «контейнер должен быть в сети X» (по конфигу) — разные утверждения. Отладка ломается там, где их путают |
| ☐ | **Агентный харнесс** | Агент видит файлы, запускает команды, работает циклом — в отличие от чата. И: любое его утверждение проверяется руками |

## Что в этот пак сознательно не входит

Kubernetes · Terraform · Ansible · облака · TLS и сертификаты · Prometheus и метрики · SLO · оркестрация · сети за пределами Docker (VLAN, маршрутизация, firewall на уровне хоста)

Всё это придёт. Три из перечисленного — уже в сентябре и октябре. Сейчас оно конкурирует за те же 20 часов с тем, без чего не работает.
