# Часть 1 · Сети и сокеты в Linux: почему так

## Почему в Linux сокет — это файл, и зачем нужен `ss` вместо `netstat`

В Unix-подобных операционных системах соблюдается классический принцип: *«всё есть файл»*. Сетевое соединение для процесса — это файловый дескриптор (socket file descriptor). Процесс открывает сокет, привязывает его к адресу и порту (`bind`), переводит в режим ожидания (`listen`) и принимает входящие пакеты через системные вызовы ядра.

Раньше для просмотра сетевых соединений использовали `netstat`. `netstat` читал текстовые файлы в псевдофайловой системе `/proc/net/dev`, `/proc/net/tcp`. Когда на сервере тысячи открытых соединений, парсинг текстового `/proc` ядром становится крайне медленным и создаёт блокировки.

Утилита **`ss` (Socket Statistics)** использует интерфейс **Netlink** — прямой бинарный протокол общения с ядром Linux. Поэтому `ss` выполняется мгновенно даже при десятках тысяч соединений.

## Зачем нужны флаги `ss -tulpn` («туплин»)

Эту команду спрашивают на каждом техническом скрининге. Каждый флаг отвечает за строгую фильтрацию в ядре:
- `-t` (**TCP**) — фильтровать только TCP-сокеты.
- `-u` (**UDP**) — фильтровать UDP-сокеты (DNS, DHCP, WireGuard).
- `-l` (**Listening**) — показывать только сокеты, которые слушают входящие подключения (вместо сотен ESTABLISHED клиентских соединений).
- `-p` (**Processes**) — показать имя процесса и его PID (требует `sudo`, иначе ядро скроет чужие процессы).
- `-n` (**Numeric**) — не тратить время на обратный резолвинг IP в доменные имена и номеров портов в названия служб (показывать `80`, а не `http`).

## `0.0.0.0` против `127.0.0.1`: в чем фундаментальная разница

- `127.0.0.1` (loopback) — пакеты не покидают стек ядра хоста. Если сервис слушает `127.0.0.1:5000`, к нему невозможно подключиться ни с другой ВМ, ни из внешней сети, ни из браузера хост-машины.
- `0.0.0.0` (INADDR_ANY) — ядро принимает пакеты на этот порт, пришедшие на **любой** активный сетевой интерфейс хоста (eth0, eth1, docker0, host-only).

Когда в Docker Compose ты объявляешь `ports: "80:5000"`, Docker по умолчанию привязывает прокси к `0.0.0.0:80`.

## Маршрутизация пакетов: почему второй адаптер ломает шлюз по умолчанию

В ядре Linux таблица маршрутизации (`ip route`) определяет, через какой интерфейс и какой шлюз (`gateway`) отправлять пакет, если адрес назначения не находится в локальной подсети.

Шлюз по умолчанию (`default via X.X.X.X dev eth0`) может быть только один с наименьшей метрикой.
Когда ты добавляешь второй сетевой адаптер в VirtualBox (например, Host-Only для локальной связи ВМ и NAT для интернета), DHCP-сервер виртуализатора может прислать маршрут `default` со второго адаптера. Если этот шлюз не имеет выхода в интернет, исходящие пакеты уходят в «черную дыру».

## Трёхстороннее рукопожатие TCP (3-way handshake) и сокеты

Установление TCP-соединения между клиентом и слушающим сокетом всегда проходит через трёхстороннее рукопожатие:
1. `SYN` — клиент отправляет запрос на синхронизацию sequence number.
2. `SYN-ACK` — сервер подтверждает получение и отправляет свой sequence number.
3. `ACK` — клиент подтверждает получение, и соединение переходит в статус `ESTABLISHED`.

Если на шаге `SYN` сервис не слушает порт, ядро вернёт пакет с флагом `RST` (Connection refused). Если пакет заблокирован фаерволом (iptables/nftables) с политикой `DROP`, клиент получит таймаут. Понимание фаз рукопожатия позволяет за 10 секунд с помощью `tcpdump` локализовать точку сбоя.

# Часть 2 · Observability и Prometheus: почему Pull-модель

## Почему Pull, а не Push

В классическом мониторинге (Zabbix Trapper, Graphite) сервисы сами отсылают (Push) метрики на центральный сервер.
Prometheus выбрал обратную модель: **Pull** — сервер мониторинга сам регулярно приходит по HTTP на эндпоинт `/metrics` каждого приложения и скрапит (собирает) данные.

**Преимущества Pull-модели:**
1. **Детектирование падений:** Если сервис упал или завис, он перестает отвечать на GET-запрос Prometheus. Сервер сразу фиксирует `up == 0`. В Push-модели при падении сервис просто затихает, и серверу трудно отличить сбой от задержки сети.
2. **Защита мониторинга от перегрузки:** Сервер опрашивает цели с заданной частотой (например, раз в 15 секунд). Если под высокой нагрузкой приложение генерирует 10 000 RPS, Prometheus не захлебнется входящими пакетами.
3. **Простота отладки:** Любой экспортер можно проверить руками обычной командой `curl http://<node-ip>:9100/metrics`.

## `node_exporter` против `cAdvisor`: разделение ответственности

- **`node_exporter`** собирает метрики хостовой операционной системы из `/proc` и `/sys`: загрузку ядер CPU, занятость RAM, I/O дисков, сетевой трафик сетевых карт. Но он не знает, какой именно контейнер потребляет память.
- **`cAdvisor` (Container Advisor)** подключается к контрольным группам Linux (cgroups) и Docker daemon (`/var/run/docker.sock`), считывая точные лимиты и потребление каждого отдельного контейнера.

# Часть 3 · CI/CD: почему `:latest` запрещен в проде

## Иммутабельность артефактов доставки

Образ контейнера — это бинарный артефакт. Если ты собираешь образ с тегом `:latest`:
1. Невозможно понять, какой именно коммит исходного кода сейчас запущен на сервере.
2. При падении невозможно выполнить команду отката (`rollback`) на предыдущую стабильную версию, потому что старый `:latest` затерся новым.
3. Локальный кэш `docker compose pull` может решить, что образ с именем `:latest` уже скачан, и пропустить обновление слоев.

Использование `$CI_COMMIT_SHORT_SHA` гарантирует однозначную связь между коммитом в Git и запущенным контейнером в продакшене.

# Часть 4 · Архитектура Observability: как строить схему и читать потоки данных

## Почему схему нужно строить послойно

На собеседовании или при защите архитектурного решения инженер часто получает маркер и доску со словами: *«Нарисуй архитектуру мониторинга твоего продакшна»*.

Хаотичный рисунок без четких границ и направлений стрелок выдает поверхностное понимание. Профессиональная схема строится строго по 10 уровням абстракции:

1. **Физический уровень узлов (Nodes & VMs):** Четкое разделение ответственности между ВМ (`vm1-app`, `vm2-monitoring/gitlab`, `vm3-runner`).
2. **Сетевые контуры (Network Boundaries):** Изоляция сетей (Host-Only для локального доступа, Internal для приватного интерконнекта, NAT для выхода в мир).
3. **Прикладной уровень (Application Workloads):** Контейнеры и демоны с указанием портов (`80`, `5000`, `5432`, `6379`).
4. **Агенты сбора метрик (Exporters):** Системный `node_exporter` (`:9100`) для ОС и контейнерный `cAdvisor` (`:8080`) для cgroups Docker.
5. **Сервер Prometheus (Scraper & TSDB):** Сборщик метрик, локальная база временных рядов (TSDB с WAL) и PromQL API (`:9090`).
6. **Потоки Pull Scrape:** Стрелки опроса направлены **от Prometheus к таргетам**.
7. **Алертинг (Alertmanager & Telegram):** Вычисление правил алертинга $\to$ отправка в Alertmanager (`:9093`) $\to$ группировка и дедупликация $\to$ Webhook в Telegram Bot.
8. **Потоки логов (Loki & Promtail):** Контраст с метриками — логи передаются по модели **Push** (`Promtail` $\to$ `Loki :3100`).
9. **Слой визуализации (Grafana):** Единое окно дашбордов (`:3000`), делающее запросы по PromQL в Prometheus и по LogQL в Loki.
10. **Легенда и протоколы:** Цветовое кодирование стрелок, исключающее двусмысленность при чтении схемы.
