## Зачем именно это, а не что-то другое

В прошлом паке ты починил связность и собрал первый образ. Но образ остался лежать в реестре контейнеров:
1. **Замкнуть контур доставки.** Пока деплой выполняется руками по SSH через терминал, у тебя не система непрерывной доставки (CD), а ручной сборочный цех.
2. **Научиться откатываться (Rollback).** Уметь выкатить код — лишь половина инженерного навыка. Вторая половина — гарантированно и быстро вернуть рабочую версию, когда релиз уронил прод.
3. **Начать работать через PR/MR (Культура изменений).** Никаких прямых пушей в main. Каждое изменение оформляется через Merge Request с явным описанием рисков и плана отката (Правило №2).

# ТРЕК 1 — СБОРКА И ОПТИМИЗАЦИЯ

## 2.1 Сборка и оптимизация Docker-образа (Multi-stage) · Слот A · ~4 ч · ВХОДИТ В МИНИМУМ

### Зачем
Большие Docker-образы (содержащие gcc, git, pip-кэш, исходники) медленно передаются по сети между runner и целевым сервером, расходуют дисковое пространство и содержат уязвимости. Multi-stage сборка разделяет фазу сборки зависимостей и чистый минимальный runtime-образ.

### Что сделать руками
1. Перепиши `Dockerfile` приложения `simpleapp` с использованием multi-stage сборки:
   - **Stage 1 (`builder`):** установка компиляторов, сборка wheel-пакетов / зависимостей Python.
   - **Stage 2 (`runtime`):** чистый базовый образ `python:3.11-slim` или `alpine`, копирование только готовых библиотек (`COPY --from=builder ...`).
2. Создай системного непривилегированного пользователя:
   ```dockerfile
   RUN addgroup -S appgroup && adduser -S appuser -G appgroup
   USER appuser
   ```
3. Добавь встроенную инструкцию `HEALTHCHECK`:
   ```dockerfile
   HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
     CMD wget --no-verbose --tries=1 --spider http://127.0.0.1:5000/health || exit 1
   ```
4. Убедись, что итоговый размер образа не превышает **100 MB**, а внутри контейнера процесс не работает от `root`.

**Готово когда:** Итоговый образ весит <100MB, контейнеры запускаются под `appuser`, а команда `docker inspect` возвращает статус `healthy`.

# ТРЕК 2 — НЕПРЕРЫВНАЯ ДОСТАВКА (CD) И ОТКАТ

## 2.2 Непрерывная доставка по SSH в GitLab CI · Слот A · ~5 ч · ВХОДИТ В МИНИМУМ

### Зачем
Ручной ввод команд на продакшн-сервере приводит к человеческим ошибкам и дрейфу конфигураций. Автоматический пайплайн должен самостоятельно подключаться к целевому серверу по SSH и обновлять контейнеры строго по commit SHA.

### Что сделать руками
1. В `.gitlab-ci.yml` объяви стадии: `build` и `deploy`.
2. Настрой версионирование по SHA:
   ```yaml
   variables:
     IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
   ```
3. В настройках GitLab репозитория (Settings -> CI/CD -> Variables) сохрани защищенные переменные:
   - `SSH_PRIVATE_KEY` (приватный ключ в формате PEM)
   - `DEPLOY_HOST` (IP-адрес `vm1-simpleapp`)
   - `DEPLOY_USER` (пользователь с правами на Docker)
4. В стадии `deploy` реализуй безопасное подключение через `ssh-agent`:
   ```yaml
   deploy:
     stage: deploy
     image: alpine:latest
     before_script:
       - apk add --no-cache openssh-client
       - eval $(ssh-agent -s)
       - echo "$SSH_PRIVATE_KEY" | tr -d '\r' | ssh-add -
       - mkdir -p ~/.ssh && chmod 700 ~/.ssh
       - ssh-keyscan -H "$DEPLOY_HOST" >> ~/.ssh/known_hosts
     script:
       - ssh $DEPLOY_USER@$DEPLOY_HOST "docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY"
       - ssh $DEPLOY_USER@$DEPLOY_HOST "export IMAGE_TAG=$IMAGE_TAG && docker compose pull && docker compose up -d"
   ```
5. Сделай коммит в репозиторий, проверь прохождение пайплайна и убедись, что на сервере запущен именно этот коммит.

**Готово когда:** Пуш в main автоматически обновляет контейнер на `vm1`, а статус деплоя отображается зеленым в GitLab CI.

## 2.3 Быстрый детерминированный откат (Rollback Runbook) · Слот A · ~3 ч · ВХОДИТ В МИНИМУМ

### Зачем
Когда новый релиз содержит критический баг, инженер не должен в панике искать команды. У тебя должен быть готовый, протестированный runbook и понимание, как откатить версию сервиса за 60 секунд.

### Что сделать руками
1. Создай инструкцию `docs/runbook-rollback.md` с пошаговыми действиями:
   - Как определить предыдущий стабильный commit SHA.
   - Команда экстренного деплоя старого образа через SSH:
     `IMAGE_TAG=<STABLE_SHA> docker compose up -d`
   - Как проверить доступность приложения после отката.
2. Проведи симуляцию аварии:
   - Выкати заведомо сломанный коммит (например, приложение завершается с exit 1 при старте).
   - Засеки время по таймеру и выполни откат по своему ранбуку.
   - Зафиксируй Time to Recovery (TTR).

**Готово когда:** Ты можешь с закрытыми глазами откатить стенд на прошлую версию менее чем за 1 минуту по своему `runbook-rollback.md`.

# ТРЕК 3 — ПРАКТИКИ И РАСШИРЕНИЕ

## 2.4 PR Conventions (Конституция практики, Правило №2) · Слот C · ~2 ч

### Что сделать
Все изменения в проекте теперь оформляются исключительно через Merge Request. Шаблон каждого MR должен содержать три обязательных поля:
1. **Что меняется:** (краткое описание архитектурного или кодового изменения).
2. **Радиус поражения (Blast Radius):** (что может пойти не так, если в коде ошибка).
3. **План отката (Rollback Plan):** (конкретная команда возврата к стабильному состоянию).

Сделай минимум 4 MR в таком формате и влей их в репозиторий.

## 2.5 [+] Nginx Reverse Proxy и заголовки · Слот D · ~2 ч · РАСТЯЖКА

### Что сделать
1. Разбери конфигурацию reverse proxy в Nginx:
   ```nginx
   proxy_set_header Host $host;
   proxy_set_header X-Real-IP $remote_addr;
   proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
   proxy_set_header X-Forwarded-Proto $scheme;
   ```
2. Объясни, почему без заголовка `Host` бэкенд не может определить виртуальный хост, а без `X-Forwarded-For` бэкенд видит IP-адрес самого Nginx вместо реального клиента.
3. Проверь логи Nginx и приложения при входящих запросах.
