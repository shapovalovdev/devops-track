# TRACK 1 — FOUNDATIONS: Networking, Sockets, and Routing

## 1.1 Linux Network Diagnostics and Sockets · Slot C/D · ~3 h · MINIMUM

### Why
When a service is unreachable or a container fails to start due to a port conflict, you must diagnose the issue in 30 seconds: is the process listening, on which interface (127.0.0.1 vs 0.0.0.0), and how is the kernel routing the traffic?

### What to do by hand
1. On host `vm1-simpleapp`, run:
   ```bash
   sudo ss -tulpn
   ```
   Break down every flag: `-t` (TCP), `-u` (UDP), `-l` (listening), `-p` (process/PID), `-n` (numeric ports/IPs). Understand TCP handshake states.
2. Find the process listening on port 80 via `lsof`:
   ```bash
   sudo lsof -i :80
   sudo lsof -i -P -n | grep LISTEN
   ```
3. Inspect kernel routing:
   ```bash
   ip route show
   ip route get 8.8.8.8
   ip route get 192.168.56.10
   ```
   Understand why adding a second virtual network adapter (NAT for internet + Host-Only for inter-VM traffic) can overwrite the default gateway (`default via ...`).
4. Write down your findings and cheat sheet in `docs/network-cheatsheet.md` in your repository.

**Done when:** You can explain `ss -tulpn` from memory and articulate the exact difference between `0.0.0.0:80` and `127.0.0.1:80`.

## 1.2 Building the Monitoring Architecture Diagram (Excalidraw) · Slot C · ~3.5 h · MINIMUM

### Why
An engineer who cannot sketch and explain the architecture of their own observability system looks unconvincing in an interview. Diagrams generated by random AI prompts are typically visually messy and omit critical telemetry flows.

A diagram crafted step-by-step by hand in Excalidraw is a cornerstone visual artifact for your portfolio. You will be able to present it during technical screenings or design reviews and explain every subsystem in under 60 seconds: from the Prometheus kernel scrape loop to Telegram alert routing.

---

### Step-by-Step Diagram Construction Guide (10 Steps)

Open [Excalidraw](https://excalidraw.com) and build the topology systematically layer by layer:

#### Step 1 · Infrastructure Layer (Nodes & Virtual Machines)
1. Draw 3 virtual machines as large rectangular boxes with explicit headers:
   - **`vm1-simpleapp`** (Application Host · `192.168.56.10` / `10.10.0.10`)
   - **`vm2-gitlab`** (Monitoring & CI Host · `192.168.56.20` / `10.10.0.20`)
   - **`vm3-runner`** (CI Runner Worker · `192.168.56.30` / `10.10.0.30`)
2. Place an external **`Host Laptop`** block (Engineer Workstation / Browser) with IP `192.168.56.1`.

#### Step 2 · Network Boundaries & Subnet Isolation
1. Delineate network interfaces and subnets using colored dashed containers:
   - **`Host-Only Network`** (`192.168.56.0/24`) — isolated access from the host laptop (`eth1` on each VM).
   - **`Internal Network`** (`10.10.0.0/24`) — private high-speed interconnect between VMs (`eth2`).
   - **`NAT Gateway`** (`10.0.2.0/24`) — virtual router for outbound Internet egress (`eth0`).
2. Inside each VM, illustrate the internal **`Docker Bridge`** network (`172.18.0.0/16`).

#### Step 3 · Workload Services & Containers
Place the application containers and system daemons inside their respective VMs with internal and published ports:
- On **`vm1-simpleapp`**:
  - `Nginx Reverse Proxy` (ports `:80`, `:443`)
  - `Simpleapp Backend (Flask/FastAPI)` (port `:5000`)
  - `PostgreSQL Database` (port `:5432`)
  - `Redis Cache` (port `:6379`)
- On **`vm2-gitlab`**:
  - `GitLab CE Web & SSH` (ports `:80`, `:22`)
  - `GitLab Container Registry` (port `:5050`)
- On **`vm3-runner`**:
  - `GitLab Runner Daemon` (systemd service)
  - `Docker Daemon (dind)` (`/var/run/docker.sock`)

#### Step 4 · Telemetry Agents & Exporters on Nodes
On each node, place the telemetry collection agents:
1. **`node_exporter` (port `:9100`)** — add to ALL 3 VMs (`vm1`, `vm2`, `vm3`). Show with small arrows that it inspects `/proc` and `/sys` host kernel files (CPU, RAM, Disk I/O, Network).
2. **`cAdvisor` (port `:8080`)** — add to `vm1-simpleapp` and `vm3-runner`. Show that it inspects container limits via `/var/run/docker.sock` and `/sys/fs/cgroup`.
3. **`Promtail` (port `:9080`)** — add to `vm1-simpleapp` for scraping `/var/log` and Docker JSON container logs.

#### Step 5 · Prometheus Server (Scrape Engine & TSDB)
On `vm2-gitlab`, place the **`Prometheus Server`** block (port `:9090`). Detail its internal architecture:
- **Retrieval Engine (Scraper):** Target polling scheduler (Scrape Loop running every `15s`).
- **TSDB (Time Series Database):** On-disk metric storage (`/prometheus/data`, 2-hour data blocks, WAL journal).
- **PromQL HTTP API / Web UI:** Expression evaluation engine and query interface (port `:9090`).

#### Step 6 · Metric Ingestion Flows (Pull Scrape Model)
Draw directional arrows for metric collection with explicit protocols and endpoints:
- Arrows point **FROM Prometheus TO targets** (representing the **Pull** model where Prometheus initiates HTTP GETs):
  - `Prometheus` $\xrightarrow{\text{HTTP GET :9100/metrics}}$ `node_exporter` (`vm1`, `vm2`, `vm3`).
  - `Prometheus` $\xrightarrow{\text{HTTP GET :8080/metrics}}$ `cAdvisor` (`vm1`, `vm3`).
  - `Prometheus` $\xrightarrow{\text{HTTP GET :9090/metrics}}$ `Prometheus (Self-monitoring)`.
- Annotate the scrape cadence: `scrape_interval: 15s`.

#### Step 7 · Alerting Engine: Alertmanager & Telegram
1. On `vm2-gitlab`, place the **`Alertmanager`** block (port `:9093`).
2. Draw the alert dispatch flow:
   - `Prometheus (Rule Evaluation Loop)` $\xrightarrow{\text{HTTP POST :9093/api/v2/alerts}}$ `Alertmanager` (triggered alert events such as `up == 0` for 2m).
3. Annotate Alertmanager functions: Deduplication, Grouping, Silencing, and Inhibition.
4. Draw outbound notification stream:
   - `Alertmanager` $\xrightarrow{\text{HTTPS Webhook / API}}$ **`Telegram Bot API`** $\to$ Engineer Alert Channel (`@alerts_channel`).

#### Step 8 · Log Ingestion Flow (Loki & Promtail) for Architectural Contrast
To clearly illustrate the contrast between **Pull metrics** and **Push logs**:
1. On `vm2-gitlab`, place the **`Loki`** service (port `:3100`).
2. Draw the **Push log** arrow:
   - `Promtail (vm1)` $\xrightarrow{\text{HTTP POST :3100/loki/api/v1/push}}$ `Loki`.
3. Add a callout: *"Metrics are gathered via Pull (Prometheus scrapes), while Logs are shipped via Push (Promtail pushes)"*.

#### Step 9 · Visualization Layer (Grafana & User Access)
1. On `vm2-gitlab`, place the **`Grafana`** block (port `:3000`).
2. Draw Data Source connections:
   - `Grafana` $\xrightarrow{\text{PromQL}}$ `Prometheus` (port `:9090`).
   - `Grafana` $\xrightarrow{\text{LogQL}}$ `Loki` (port `:3100`).
3. Draw inbound access paths from `Host Laptop`:
   - `Engineer Browser` $\xrightarrow{\text{HTTP :3000}}$ `Grafana Dashboards` (primary operational interface).
   - `Engineer Browser` $\xrightarrow{\text{HTTP :9090}}$ `Prometheus Web UI` (raw PromQL query debugging).

#### Step 10 · Legend, Hygiene & Artifact Export
1. Place a **Legend** card in the corner with arrow color conventions:
   - 🔵 **Blue:** Metric Pull (HTTP GET `/metrics`).
   - 🟣 **Purple:** Log Push (HTTP POST `/loki/api/v1/push`).
   - 🟠 **Orange:** Alerting & Notifications (Alertmanager $\to$ Telegram).
   - 🟢 **Green:** User / Application Traffic (Browser $\to$ Nginx $\to$ App).
2. Verify font clarity, block alignments, and ensure zero overlapping labels.
3. Export the diagram in both **PNG** (clean white/transparent background) and **SVG** formats.
4. Save the artifact to your repository: `assets/stand-topology-v2.png`.

# TRACK 2 — PRACTICE: Prometheus and Metric Collection

## 2.1 Prometheus from Scratch + node_exporter on 3 VMs · Slot A · ~5 h · MINIMUM

### Why
Loki collects log streams (events of what happened), while Prometheus collects numerical time-series metrics (how the system behaves right now). Prometheus's pull model allows the monitoring server to actively scrape targets and reliably detect down nodes.

### What to do by hand
1. On `vm2-gitlab`, create `prometheus.yml`:
   ```yaml
   global:
     scrape_interval: 15s
     evaluation_interval: 15s

   scrape_configs:
     - job_name: 'prometheus'
       static_configs:
         - targets: ['localhost:9090']

     - job_name: 'node'
       static_configs:
         - targets:
             - '192.168.56.10:9100'  # vm1-simpleapp
             - '192.168.56.20:9100'  # vm2-gitlab
             - '192.168.56.30:9100'  # vm3-runner
   ```
2. Deploy Prometheus via `docker-compose.yml` on `vm2`.
3. Install and run `node_exporter` (v1.8+) across all three virtual machines.
4. Navigate to `http://<prometheus-ip>:9090/targets` in your browser and confirm that all 3 endpoints report **UP (1/1)**.

**Done when:** All 3 VMs stream OS metrics into Prometheus, and every target in `/targets` shows green.

## 2.2 Container Monitoring via cAdvisor · Slot A · ~3 h

### Why
`node_exporter` observes the host OS, but lacks visibility into individual Docker containers. If an application container exceeds memory limits and is OOMKilled by the kernel, `cAdvisor` isolates that container's resource spike.

### What to do by hand
1. On `vm1-simpleapp`, run `gcr.io/cadvisor/cadvisor:latest` with mounts for `/var/run/docker.sock` and system cgroup directories (`/sys`, `/var/lib/docker`).
2. Add a `cadvisor` scrape job to `prometheus.yml` on `vm2`.
3. Verify metrics in the Prometheus Expression Browser:
   - `container_cpu_usage_seconds_total`
   - `container_memory_usage_bytes`

**Done when:** Prometheus scrapes per-container telemetry for simpleapp, redis, and nginx containers.

## 2.3 Eliminating CI/CD Debt: Commit SHA Versioning · Slot C · ~2 h

### Why
Deploying with `:latest` in CI/CD is an antipattern: you cannot track code origin, cannot perform atomic rollbacks, and Docker caching may pull stale layers.

### What to do by hand
1. In `.gitlab-ci.yml`, set:
   ```yaml
   variables:
     IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
   ```
2. Update the `build` and `deploy` stages to use `$IMAGE_TAG`.
3. In `docker-compose.yml` on `vm1`, point to the versioned image.
4. Push a commit, verify pipeline execution, and inspect `docker ps` on `vm1` to ensure the container runs the short commit hash.

**Done when:** Every commit builds an image tagged with its short commit SHA, and the runner deploys that specific artifact.

## 3.1 [+] Basic PromQL · Slot D · ~2 h · STRETCH

### What to do
Write and record 5 PromQL queries in Prometheus UI:
1. Host CPU utilization percentage over 5 minutes:
   `100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)`
2. Available RAM percentage:
   `(node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100`
3. Free root filesystem disk space percentage:
   `node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"} * 100`
4. Network ingress throughput (bytes/sec):
   `rate(node_network_receive_bytes_total[5m])`
5. Host down alert query:
   `up == 0`
